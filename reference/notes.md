### Important: the real model weights have never actually been loaded

This whole session ran in a sandboxed remote environment whose egress
policy blocks `huggingface.co` outright (confirmed via the proxy's status
endpoint — a policy-level 403, not a fixable client/TLS issue, and not
something worth retrying). Only a handful of package registries (PyPI,
npm, etc.) were reachable. **Every Phase 2 test used a synthetic toy
safetensors file, not the real thing.**

This matters more than it might sound like, for one specific reason: the
toy file's tensor names and shapes were generated by calling the *same*
`expectedTensorShapes()` function that `safetensors.js`'s `validateHeader()`
checks against (see the now-deleted scratch script that built it — it
imported the same shape logic). That test can prove the mechanics are
right — header parsing, bf16 decode, per-row int8 quantization, ranged
fetch + concurrency, IndexedDB caching — but it **cannot** catch a wrong
assumption baked into that shared function itself. Specifically still
unverified against a real file:

- The exact tensor names (`model.embed_tokens.weight`,
  `model.layers.N.self_attn.q_proj.weight`, etc.) — this is standard
  HF Llama-family state_dict convention, but "standard" isn't "confirmed."
- The literal dtype string in the header (assumed `"BF16"`).
- That `lm_head.weight` really is absent (resting on `tie_word_embeddings`
  + convention, per gotcha 3 in plan.md).
- The header-probe-too-small path (`needsMoreBytes` in `parseHeader`) —
  unit-tested with a hand-crafted truncated buffer, never exercised by a
  real header. A real 135M header is probably ~35-40KB (~270 tensors),
  comfortably under the 200KB probe, so this path likely won't even
  trigger on the real file — it'll stay unit-test-only unless the 360M's
  header turns out bigger than expected.
- Real HF CDN behavior under the loader's bounded concurrency (4
  simultaneous Range requests) — whether it 206s reliably every time,
  rate limits, etc.

None of this fails silently if wrong — `validateHeader()` throws a loud,
specific error naming exactly what's missing or mismatched. But it means
**the first real run against `huggingface.co` is still a real test**, not
a formality. Recommended first step on a machine with real internet
access: fetch just the header (a `Range: bytes=0-102399` request against
`model.safetensors`) and sanity-check the tensor names before trusting a
full load.

### Phase 5's real gate needs a machine with internet access

Phase 5's exit criterion (`plan.md` §5) is matching golden logits from an
actual Python + `transformers` forward pass on the real weights. That
can't be produced from this sandboxed session — it needs `transformers`
+ `torch` + `safetensors` and the real model files, none of which are
reachable here. This has to happen on a machine that can actually reach
Hugging Face (e.g. the desktop handoff being planned as of this note).

### What *was* verified against real ground truth

Phases 3 and 4 are on much firmer footing than Phase 2, because their
ground truth doesn't require the model weights — only the tokenizer files
already committed to `reference/`:

- `pip install tokenizers jinja2` worked fine in this sandbox (PyPI is
  allowlisted even though huggingface.co isn't).
- `reference/golden/tokenizer_cases.json` was generated by loading the
  real `reference/135M/tokenizer.json` with the actual `tokenizers`
  library and encoding 23 test strings (emoji, unicode accents, digit
  runs, decimals, negatives, contractions, partial/adjacent special
  tokens, whitespace edge cases). The hand-written JS tokenizer matches
  every one of them exactly, both encode and round-trip decode.
- `reference/golden/chat_template_cases.json` was generated by rendering
  the actual `chat_template` string from `tokenizer_config.json` with
  real Jinja2, for 4 message sets x {with, without} generation prompt.
  The hardcoded JS template matches character-for-character, and
  re-tokenizing the output matches the reference token ids exactly.

These two golden files are committed and can be re-run against the JS
implementation at any time as a regression check — see the test approach
below.

### How things were actually tested this session

Nothing here is committed as a repeatable test suite yet — there's no
`tests/` directory in the repo. Everything below ran as ad hoc scripts
in this session's scratch directory and was **not** persisted. If durable
regression tests are wanted going forward, they need to be (re)built
properly, not assumed to already exist:

- **Pure-function unit tests** (Node, no DOM): `decodeBf16` round-trip and
  sign handling, `quantizeRowsInt8` per-row scales and the all-zero-row
  edge case, `parseHeader`'s truncated-buffer path, `validateHeader`'s
  missing/mismatched-tensor detection, `expectedTensorShapes`'s
  head_dim-divisibility check.
- **Headless-browser integration tests** (Playwright + Chromium,
  pre-installed at `/opt/pw-browsers/chromium` in this environment):
  served the static site locally, used `page.route()` to mock
  `huggingface.co` requests (including real `Range`/206 handling), and
  drove the actual click-to-ready UI flow. Confirmed: fresh load issues
  exactly one HEAD + one GET per tensor, a reload hits the IndexedDB
  cache with zero additional network requests, and a full run against
  the *real* production `vocab.json`/`merges.txt` (49,152 entries) with
  a toy model file produces zero console errors end to end.
- **Tokenizer/template correctness**: compared directly against the
  golden JSON files described above (these ones are committed and
  reusable).

### Other deviations / things worth knowing

- **IndexedDB schema changed between Phase 1 and Phase 2.** Phase 1 used
  a single `"models"` object store holding one raw whole-file blob per
  model. Phase 2 replaced this entirely with `"tensors"` (one record per
  tensor) + `"manifests"` (one record per model+dtype), and bumped
  `DB_VERSION` to 2 with an `onupgradeneeded` handler that deletes the old
  `"models"` store if present. If you have a browser profile that ran the
  Phase-1-only version of this app, its cached data is gone on next load
  (by design — it was always meant to be replaced, not migrated).
- **`main.js` hardcodes `DTYPE = "i8"`.** The `'f32'` (dequantize-only,
  no quantization) path exists in `safetensors.js` and is exercised by
  the pure-function unit tests, but nothing in the UI currently lets you
  load a model as f32. Phase 5's "run in f32 first, validate against
  golden logits" step will probably want this exposed — either as a
  second button/flag, or just called directly when wiring up
  `transformer.js`.
- **Special tokens are hardcoded** in `tokenizer.js` (17 strings) rather
  than read from `tokenizer.json`, specifically to avoid fetching that
  2.1MB file just for a list of 17 short strings. Verified identical
  between both models' `tokenizer.json` files. If a future model ever
  gets added to this project with different special tokens, this list
  needs to change by hand.
- **Bounded concurrency for tensor loading is 4** (`CONCURRENCY` in
  `safetensors.js`), chosen to keep peak memory near "final size" per
  plan.md's Phase 2 requirement, but never load-tested against the real
  CDN. Worth watching (via the Network tab) the first time a real 360M
  load runs, in case HF's server has opinions about many small ranged
  requests in flight.
